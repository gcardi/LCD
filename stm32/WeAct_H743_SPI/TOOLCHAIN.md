# STM32 Project Origins and Toolchain

This guide explains how the `WeAct_H743_SPI` firmware project was created,
which files are generated, which are handwritten, and how to regenerate it
without losing manual work. See the [README](README.md) for wiring, builds,
programming, and test results.

## Project origins

The project was created with **STM32CubeMX 6.18.1** (database
`DB.6.0.181`), using **CMake** code generation rather than STM32CubeIDE or
Makefiles. `WeAct_H743_SPI.ioc` is the source of truth for pin assignments,
clocks, and peripherals.

| Item | Value |
|---|---|
| MCU | STM32H743VIT6, LQFP100 (`Mcu.UserName=STM32H743VITx`) |
| Board | WeAct MiniSTM32H743, defined as `board=custom` |
| Firmware package | STM32Cube FW_H7 V1.13.0 |
| Target toolchain | `ProjectManager.TargetToolchain=CMake` |
| SYSCLK | 480 MHz |
| Peripherals | SPI2 full-duplex master, DMA1 (SPI2_TX, SPI2_RX), GPIO |

The relevant Project Manager settings are `KeepUserCode=true`,
`BackupPrevious=true`, and `CoupleFile=true`. They preserve `USER CODE`
sections, save previous versions under `Core/*/Backup/*.bak`, and keep one
file per peripheral (`gpio.c`, `spi.c`, and `dma.c`).

## Development environment

Open the project in **Visual Studio Code** with ST's official *STM32CubeIDE for
Visual Studio Code* extension. The development setup uses
`stmicroelectronics.stm32cube-ide-build-cmake` 1.46.0, `-build-analyzer`
1.4.0, `-bundles-manager` 1.4.0, and `-clangd` 1.0.6, alongside
`ms-vscode.cmake-tools`, `ms-vscode.cpptools`, and `marus25.cortex-debug`.
The third-party `bmd.stm32-for-vscode` extension is not needed and should
remain disabled to avoid conflicting configurations.

| Tool | Version | Source |
|---|---|---|
| STM32CubeCLT | 1.17.0 | `C:\ST\STM32CubeCLT_1.17.0` |
| arm-none-eabi-gcc | 12.3.1 (GNU Tools for STM32 12.3.rel1) | CubeCLT |
| STM32_Programmer_CLI | included with CubeCLT | used by `build.ps1` |
| CMake | 4.1.1 | PATH |
| Ninja | 1.13.2 | PATH |

`build.ps1` looks for `STM32_Programmer_CLI.exe` on `PATH`, then under
`C:/ST/STM32CubeCLT_*/STM32CubeProgrammer/bin/`. Use `-ProgrammerPath` for
another installation. The compiler, CMake, and Ninja must be on `PATH`; the
toolchain file does not hard-code their absolute paths.

Builds and uploads use the project's PowerShell scripts, which are also exposed
as VS Code tasks in `.vscode/tasks.json`. This keeps the workflow identical in
VS Code, at a terminal, and in a future CI system. No `launch.json` is
committed: configure ST-LINK debugging locally with cortex-debug or ST's
debugger.

## File ownership

**Regenerated by CubeMX on every Generate Code** (do not edit outside
`USER CODE` sections):

- Generated `Core/Inc/*.h` and `Core/Src/*.c`: `main`, `gpio`, `spi`,
  `dma`, `stm32h7xx_it`, `stm32h7xx_hal_msp`, `stm32h7xx_hal_conf`,
  `system_stm32h7xx`, `syscalls`, and `sysmem`.
- `Drivers/` (HAL/LL and CMSIS), `startup_stm32h743xx.s`, and
  `STM32H743xx_FLASH.ld`.
- `cmake/stm32cubemx/CMakeLists.txt`, which lists sources, includes, and macros.
- `Core/*/Backup/*.bak`, containing the previous generated version.

**Generated once, then maintained by hand**:

- Top-level `CMakeLists.txt`.
- `CMakePresets.json` (`Debug` and `Release` presets, Ninja generator,
  output under `build/<preset>/`).
- `cmake/gcc-arm-none-eabi.cmake` (Cortex-M7, `fpv5-d16`, hard-float ABI).
- `cmake/starm-clang.cmake`, an alternative generated toolchain not used by the presets.

**Fully handwritten:**

- `Core/Src/spi_selftest.c`, `Core/Inc/spi_selftest.h`, and
  `Core/Inc/spi_diag_config.h`.
- `cmake/spi_dma.ld`, the supplementary linker script.
- `build.ps1`, `test-hardware.ps1`, and `diagnose-hardware.ps1`.
- `.vscode/tasks.json`, `README.md`, and this document.

Under `stm32/`, `.gitignore` excludes `build/`, object and ELF artifacts,
`compile_commands.json`, `CMakeUserPresets.json`, `.mxproject`, and local
editor state. The `.ioc` file, sources, `Drivers/`, linker scripts, and
shareable `.vscode/` files remain tracked.

## Rules for preserving changes

1. Keep application code outside generated files or inside `USER CODE BEGIN/END`
   sections. In `main.c`, the manual code only includes `spi_selftest.h` and
   calls `SPI_SelfTest_Run()` in `USER CODE BEGIN 2`.
2. Add user sources to `target_sources` in the top-level `CMakeLists.txt`,
   never to `cmake/stm32cubemx/CMakeLists.txt`, which CubeMX rewrites.
3. The `.spi_dma` section in RAM_D2 is defined in `cmake/spi_dma.ld` and
   attached with `target_link_options`; do not edit generated
   `STM32H743xx_FLASH.ld`.
4. Change pin assignments, clocks, DMA, and SPI parameters in the `.ioc`, not
   in code: CubeMX overwrites `spi.c` and `gpio.c` at the next generation.
5. After Generate Code, review the Git diff (including `.bak` files) and
   rebuild before programming the target.

## Matching the `.ioc` to the firmware

The `.ioc` matches the qualified configuration. PLL2 supplies SPI2 with a
150 MHz kernel clock; SPI2 starts as an 8-bit full-duplex master using
`SPI_BAUDRATEPRESCALER_16`, or 9.375 Mbit/s. The `BE` path temporarily uses
`/8` for 18.75 MHz TX-only transfers, while `BF` uses `/128` (1.171875 MHz)
to read MISO, then restores `/16`. CubeMX models the clock and initial state;
the two dynamic prescalers remain in application code.

NSS is software-controlled with `FPGA_CS` on PB12 (output, high at startup,
GPIO speed HIGH). SCK/MISO/MOSI use PB13/PB14/PB15 at GPIO speed MEDIUM. This
slower edge rate is deliberate: faster edges produced worse bench-test results,
as documented in [SPI_DIAGNOSTIC_RESULTS.md](../../docs/SPI_DIAGNOSTIC_RESULTS.md).
When changing the PLL, prescaler, or GPIO speed, update the `.ioc`, generated
and application code, and the FPGA SPI timing constraint together.

DMA buffers live in RAM_D2 and are aligned to 32 bytes. Generated code does not
enable the data cache, but the self-test still performs conditional
clean/invalidate operations based on `SCB->CCR`, so it remains correct if the
cache is enabled later.

`diagnose-hardware.ps1` rewrites `Core/Inc/spi_diag_config.h` to select a
diagnostic matrix; it does not modify the `.ioc`. After a diagnostic session,
restore the normal firmware with `-RestoreSelfTest`.

## Regenerating with CubeMX

1. Open `WeAct_H743_SPI.ioc` with STM32CubeMX 6.18.1 or later.
2. In Project Manager, confirm Toolchain/IDE is **CMake** and *Keep User Code
   when re-generating* is enabled.
3. Run Generate Code. Delete `build/` if the source layout changed, then run
   `./build.ps1` again.
4. Review the diff. Unexpected changes to the top-level `CMakeLists.txt` or
   `cmake/gcc-arm-none-eabi.cmake` mean CubeMX recreated them; restore the
   `spi_selftest.c` source and the `target_link_options` entry for
   `spi_dma.ld`.

## Status and limitations

The firmware currently runs only the SPI self-test against the FPGA slave; the
display protocol is not yet available. A `Release` preset exists but has not
been qualified on hardware, repository debugging is not configured, and the
READY line is not implemented. Qualification results and measured limits are in
the [README](README.md) and
[SPI_PERFORMANCE.md](../../docs/SPI_PERFORMANCE.md).
